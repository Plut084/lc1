# 物品与装备：已替代的合并提案

记录日期：2026-11-10。保留此前未实现的可选属性块提案。用户随后确认保留 Resource、Equipment、Weapon 独立定义，以统一资源编号关联；现行契约见 [资源与穿戴](../design/resources.md)。此处不是现行实现或实施计划。

## 物品与背包（设计草案，尚未实现）

> 本节讨论背包如何同时容纳材料、货币、装备。代码仍只有资源堆叠背包与独立的运行时装备对象，以下改动均未实施。

### 当前边界

- `Resource` 只有 `keyid`、`name`、`category`、`weight`（克）四个字段，定义进程期只读。
- `Bag` 是 `unordered_map<keyid, ResourceStack>` 加总重上限，只认“定义 × 数量”，不认识装备。
- 装备是独立的运行时对象，由世界继承 `unique_ptr<Equipment>`，角色用 `map<EquipmentType, Equipment*>` 借用。
- 所以铁盔有两份互不相干的记录：`catalog.hpp` 的资源 keyid 4 和 `equipments.yaml` 的装备 keyid 1。打造产物只能进背包，穿不上。

### 物品定义

能放进背包的东西共用一种定义，装备不是特例：

| 字段 | 含义 |
|---|---|
| `keyid` | 全局唯一编号，跨类别不重叠 |
| `name` | 显示名 |
| `category` | Currency / Material / Consumable，规则与分组用；不含 `Equipment` |
| `weight` | 单件重量，克 |
| `stack_limit` | 单堆上限，默认 1；装备不写，用默认值 |
| `equip` | 可选：槽位 + 属性块；有它才能装备，没有就只是普通物品 |

“是不是装备”只由 `equip` 是否有值回答，不设第二个标记。类别的恒定值不抄进每条记录（装备不写 `stack_limit = 1`），否则就是同一信息的两份副本，还得在入口校验它们一致。

属性块扁平写 `{slot, armor, attack, range}`，数值缺省即 0，不逐个包成 `optional`：头盔 `armor = 1`、`attack = 0` 是正常取值。只有武器外观需要 `optional<ModelConfig>`，因为防具当前不挂独立模型，“没有外观”和“外观为空”不是一回事。

武器、防具、饰品都是 `equip` 槽位不同的同一种定义；具体属性项见 `characters.docx` 的装备分类与 `property.docx` 的 `atk`，本节不重复数值。

一个 `Bag` 装所有类别，按 `equip` 有值先分出装备组，其余按 `category`，不做“材料包 + 装备包”的多容器。只有玩法真的需要分开上限时才拆容器。`category` 只进入规则查询，不让 `Bag` 出现按类别的分支。

不按类别拆成“通用表 + 属性表”：`optional` 在运行时没有额外成本，拆表则要为装配和存档付两张表的 join 与交叉校验，换来的只是记录里少一个空字段。

### 物品身份

默认只有“定义 × 数量”：两件铁盔完全等价，背包里就是数量 2（但装备用默认堆叠上限 1，实际是两条各 1 的条目，避免穿戴和 UI 语义含混）。

只有当某类物品需要“每件都不一样”——耐久、词缀、镶嵌、绑定——才引入实例层：`ItemId` 单调递增，`ItemId → {定义, 状态}` 存在容器所有者里，背包条目和槽位都存实例号而不是 `keyid`，存档多一张 items 表。没有这些玩法就不要建这张表，所有权、存档兼容和 UI 都要为它加一层。

### 负重

角色负重 = 背包内物品 + 穿戴中的装备（含武器）。上限就是现有存档字段 `bag_capacity`，语义从“背包上限”变为“角色负重上限”，字段名暂不改。

不改 `Bag` 的职责划分：预算仍在 `Bag`，因为打造校验只拿到背包。新增

- `bool reserve(uint32_t weight)` / `void release(uint32_t weight)`
- `uint32_t used_weight() const`（包内 + 占用）

并把 `add` 的检查改为 `used_weight() + 新增重量 <= 上限`。不变式只有一条、只有 `Bag` 一处检查；槽位表不存重量副本，重量始终来自只读定义。

- 穿戴：先 `remove` 再 `reserve`，净变化为零，两步都不可能失败。
- 卸下：先 `release` 再 `add`，同理，所以卸下的装备一定放得回背包。
- 从地面直接捡起穿上：先 `reserve` 检查，失败不占槽。
- `prepare_recipe` 复制 `Bag` 时带上占用，打造签名不用多加参数。
- 存档只写 `bag_capacity`、槽位 `keyid` 和包内条目；占用在读档时按槽位重量重新 `reserve`，不接受存档提供的重量。

默认 10 kg 需要重新评估：穿 2.5 kg 铁盔后只剩 7.5 kg，而铁盔配方原料本就有 12.2 kg。

### 存档与编号

装备、武器定义并入物品定义表后，槽位只存 `keyid`，与现有 `weapon` 写法一致，`equipments.yaml` 和 `weapons.yaml` 退役。

旧装备 keyid 1 与资源 keyid 4 冲突，迁移必须写显式映射表（旧类别 + 旧 keyid → 新 keyid），旧存档的槽位记录按表改写，不能按编号推断。存档版本升到 5。

### 待定

- 装备是否需要实例状态，决定是否引入 `ItemId` 与实例表。
- 任务物品的不可丢弃、不占重量等规则加在定义上，不加在 `Bag` 上。
- 货币是否继续留在背包内（当前是 `Currency` 资源）。
- 上面 `资源字段` 的 `ResourceType` 枚举草案与已实现的 `Resource` 不一致，需确认保留哪一种（已实现代码不使用 `ResourceType`）。
